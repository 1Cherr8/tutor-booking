# Описание проекта Tutor Booking

## 1. Назначение проекта

Tutor Booking — учебное веб-приложение для записи клиентов на индивидуальные занятия по математике и физике. Система решает простую практическую задачу: клиент может зарегистрироваться, посмотреть доступные направления занятий и создать запись на выбранную дату и время, а администратор может управлять каталогом предметов и всеми записями клиентов.

Главная цель проекта — продемонстрировать полный цикл разработки небольшого информационного сервиса: пользовательский интерфейс, серверную часть, базу данных, авторизацию и разграничение прав доступа. Все основные компоненты запускаются в Docker-контейнерах, поэтому проект можно развернуть одной командой независимо от того, какие версии PostgreSQL, Python или Node.js установлены на компьютере.

В системе предусмотрены две роли. Роль `client` предназначена для обычного пользователя. Клиент может самостоятельно зарегистрироваться, войти в систему, просматривать список предметов и работать только со своими записями. Роль `admin` предназначена для администратора. Администратор имеет расширенные права: может создавать, изменять и удалять предметы, видеть все записи клиентов и изменять их состояние.

## 2. Архитектура и технологии

Проект построен по клиент-серверной архитектуре и состоит из трёх основных частей.

**Frontend (UI).** Пользовательский интерфейс реализован на React. Он отвечает за отображение страниц входа и регистрации, списка предметов и записей, а также форм создания и редактирования данных. Frontend собирается с помощью Vite и после сборки раздаётся веб-сервером Nginx. Для пользователя интерфейс доступен в браузере по адресу `http://localhost:3000`.

**Backend (Server).** Серверная часть реализована на Python с использованием FastAPI. Backend предоставляет REST API. Через HTTP-запросы интерфейс получает данные из базы, создаёт новые объекты, изменяет и удаляет их. FastAPI также автоматически формирует интерактивную документацию API, доступную по адресу `http://localhost:8000/docs`.

**Database (DB).** Для хранения данных используется PostgreSQL. В базе есть таблицы пользователей, предметов и записей. Связь между таблицами устроена так: один пользователь может иметь много записей, один предмет также может встречаться во многих записях, а каждая запись относится к одному пользователю и одному предмету.

Для взаимодействия Python-кода с PostgreSQL используется SQLAlchemy. Он позволяет описать таблицы как классы Python и выполнять операции с базой через ORM. Подключение к PostgreSQL выполняется через драйвер psycopg.

Все три части запускаются через `docker compose`. В `docker-compose.yml` описаны контейнеры `db`, `backend` и `frontend`. Контейнер базы данных хранит данные в отдельном Docker volume, поэтому они не пропадают при обычной перезагрузке контейнеров.

## 3. Бизнес-сущности и CRUD

По заданию требуется реализовать минимум две бизнес-сущности с полным набором CRUD-операций. В проекте такими сущностями являются `Subject` и `Booking`.

### Subject — предмет или услуга

Сущность хранит название направления, описание, цену, длительность занятия и признак активности. Для неё реализованы:

- Create — администратор может добавить новый предмет;
- Read — клиент и администратор могут получить список предметов или один предмет;
- Update — администратор может изменить данные предмета;
- Delete — администратор может удалить предмет, если на него не ссылаются существующие записи.

### Booking — запись на занятие

Сущность хранит клиента, выбранный предмет, дату и время, статус и комментарий. Для неё также реализован полный CRUD:

- Create — авторизованный клиент может создать запись для себя;
- Read — клиент видит только свои записи, администратор видит все;
- Update — клиент может менять собственную запись, администратор может редактировать любую;
- Delete — клиент может удалить собственную запись, администратор — любую запись.

Таким образом, требования по двум CRUD-сущностям выполняются полностью. Пользователь является дополнительной технической сущностью, необходимой для авторизации и связи записей с конкретным клиентом.

## 4. Авторизация и права доступа

Авторизация реализована с помощью JWT-токенов. При регистрации пароль пользователя не сохраняется в открытом виде. Сервер создаёт безопасный хэш пароля с помощью библиотеки `pwdlib`. При входе введённый пароль сравнивается с сохранённым хэшем.

Если данные верны, сервер формирует JWT-токен. Frontend сохраняет его в браузере и отправляет в заголовке `Authorization` при последующих запросах. Backend проверяет токен и определяет пользователя и его роль.

Роль клиента создаётся автоматически при регистрации. Администратор создаётся сервером при первом запуске приложения. Его тестовые данные задаются переменными окружения в Docker Compose. По умолчанию используются `admin@example.com` и пароль `admin12345`. Эти значения предназначены только для демонстрации и в реальном проекте должны быть заменены.

Разграничение прав выполняется на сервере, а не только в интерфейсе. Поэтому клиент не сможет получить административный доступ, даже если вручную отправит запрос к закрытому API. Например, операции создания, изменения и удаления предметов требуют роль `admin`.

## 5. MVP и дальнейшее развитие

Для проекта сформировано 60 пользовательских сценариев в формате user stories. Из них выделены 20 основных сценариев MVP. MVP включает регистрацию и вход, работу с предметами, создание и управление собственными записями клиента, а также административный CRUD для предметов и записей.

Остальные use cases рассматриваются как дальнейшее развитие проекта. К ним относятся поиск, фильтрация, восстановление пароля, напоминания, аналитика, экспорт CSV, журнал изменений и защита от пересечения записей по времени. Такое разделение показывает разницу между минимально работоспособной версией и функциями, которые можно добавлять после проверки основной идеи.

## 6. Запуск и результат

После клонирования репозитория достаточно выполнить команду `docker compose up --build`. Docker самостоятельно скачает необходимые базовые образы, установит зависимости, создаст сеть между контейнерами и запустит PostgreSQL, FastAPI и React/Nginx.

После запуска пользователь открывает `http://localhost:3000`. Новый клиент может зарегистрироваться и пользоваться системой. Для проверки административных функций можно войти под тестовым администратором. REST API можно отдельно проверить через Swagger UI по адресу `http://localhost:8000/docs`.

В результате получено небольшое, но полноценное веб-приложение с разделением на UI, сервер и базу данных, контейнеризацией Docker, авторизацией по ролям и CRUD-операциями над двумя бизнес-сущностями. Структура проекта подходит для хранения в Git-репозитории и дальнейшего расширения.
